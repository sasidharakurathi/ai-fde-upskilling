# Lesson 0.3 · The parts of an AI app: a simple tour

**Stage 0 · The big map** · Time: about 1 hour (read 20 min · try 25 min · explain back 15 min)

## Why this lesson?
When people say "an AI app," they often imagine just the model. But the model is only **one part**.
Most of the real work, and most of the bugs, live in the parts around it. Today you'll learn those
parts, so every later stage has a clear place on the map.

---

## Our example: "Ask HR"
An employee types into a chat window:

> *"How many vacation days do I get?"*

…and gets back:

> *"You get 24 days per year (HR Policy, section 3.1)."*

Here's everything that happens in between:

```
 ① USER + INTERFACE         "How many vacation days do I get?"
        │
        ▼
 ② YOUR CODE (the backend) ── who is asking? is this person allowed? (LOGIN, Stage 12)
        │
        ├──► ③ DATA ── search the company's HR documents
        │         ◄── returns the 3 most relevant pieces of text
        │
        ▼
 ④ THE PROMPT   instructions + the found text + the question, put together as one message
        │
        ▼
 ⑤ THE MODEL (LLM)  reads the prompt, generates the answer
        │
        ▼
 ⑥ OUTPUT CHECKS ── is it safe? does it name its source? no private data?
        │
        ▼
 ① USER sees:  "You get 24 days per year (HR Policy, section 3.1)."

 ⑦ LOGS + EVALS  (in the background) record what happened; measure quality over time
```

---

## The parts, one by one

### ① User + interface
**Interface** (also called **UI**, "user interface") = the place where the user types and reads: a chat
window, a website, Slack, a mobile app.
*Plan: Stage 7 (a simple UI).*

### ② Your code (the "backend")
**Backend** = the code running on a server that connects everything. It receives the question, checks who
is asking, calls the other parts in the right order, and sends the answer back.
Think of it as the **manager** who coordinates the team. Most of an AI Engineer's code lives here.
*Plan: Stages 3, 7.*

### ③ Data
The company's own information: documents, databases, websites. The model **doesn't know** your company's HR
policy. It was never trained on it. So your code **finds** the right pieces of text and hands them to the model.
Finding the right pieces is called **retrieval** (that's the "R" in RAG).
*Plan: Stages 4, 5.*

### ④ The prompt
The **prompt** is the full message sent to the model. In a real app it is **much more** than the user's
question. It's put together by your code:

```
INSTRUCTIONS:  You are an HR assistant. Answer ONLY from the documents below.
               If the answer isn't there, say "I don't know". Always name the source.
DOCUMENTS:     [HR Policy 3.1] Full-time employees receive 24 vacation days per year...
               [HR Policy 3.4] Unused days can be carried over until March 31...
QUESTION:      How many vacation days do I get?
```
*Plan: Stage 3.*

### ⑤ The model
The LLM reads the prompt and generates the answer, one token (piece of a word) at a time, like you learned in
Lesson 0.1. It can run on a provider's servers (a **hosted API**) or on your own machine (a **local model**).
*Plan: Stages 2, 10.*

**Important: the model has no memory between calls.** Every call starts completely fresh. So how does a chat
app "remember" what you said two messages ago? **Your code re-sends the earlier conversation inside the prompt
every time.** If the code forgets to do that, the bot "forgets" too. This is called being **stateless**.

### ⑥ Output checks (guardrails)
**Guardrails** = checks that run before the user sees the answer. Does it include a source? Does it leak
private data (like someone's salary)? Is it polite? Some are simple rules (remember Lesson 0.1: rules are still
useful!).
*Plan: Stage 11.*

### ⑦ Logs + evals
**Logs** = a record of what happened (question, documents found, answer, time taken, cost).
**Evals** = tests that measure answer quality with numbers. Without these, you can't tell if a change made
things better or worse.
*Plan: Stages 6, 11.*

### Around everything: login, hosting, cost
- **Login and permissions:** an intern shouldn't get answers from the CEO-only documents. *(Stage 12)*
- **Hosting:** where the app runs (a cloud server, the customer's own network). *(Stages 7, 12)*
- **Cost:** hosted models charge for every token you send and receive, so a long prompt costs more. *(Stages 2, 11)*

## Which parts does each role focus on?
| Part | AI Engineer | FDE |
|------|-------------|-----|
| ③ Data | How to find the right text (retrieval quality) | Connecting to the *customer's* data sources |
| ④ Prompt | Writing and testing it | Adapting it to the customer's needs and wording |
| ⑤ Model | Choosing and comparing models | Whether the customer allows hosted models, or needs local |
| ⑥ Checks | Building them | Matching the customer's security rules |
| ⑦ Evals | Building and running them | Running them **on the customer's data** to prove it works |
| Login / hosting | Basic | Deep: the customer's SSO, network, security review |

Both roles must understand **every** part. They differ in which parts they go deepest on.

## Common confusions
| People think | What's actually true |
|--------------|----------------------|
| "The AI app = the model" | The model is one part out of seven. Most of the work is everything around it. |
| "The model remembers me" | It's stateless. Your code re-sends the conversation each time. |
| "Wrong answer? Get a better model." | Often the real problem is the **data** (old document), the **retrieval** (found the wrong text), or the **prompt**. Check those first. They're cheaper to fix. |
| "The prompt is what the user typed" | The real prompt = instructions + found documents + conversation history + the user's question. |

**Part A** (example):
① The customer types the question in the shop's chat window. → ② The backend receives it (and checks who's
logged in). → ③ It searches the shop's policy pages and finds the shoe-returns section. → ④ The code builds the
prompt: instructions + the returns text + the question. → ⑤ The model writes the answer. → ⑥ Checks: does it cite
the policy? no private data? → ① The customer sees the answer. ⑦ Meanwhile, logs record it all.

**Part B:**
1. **③ Data.** The documents are out of date. A better model won't fix this; updating the data will.
2. **④ Prompt.** The instructions should set the tone (e.g. "be friendly and polite").
3. **Login / permissions (in ② the backend).** The code isn't checking who is asking before fetching data. This is a serious security bug.
4. **② Your code.** The model is stateless; the code must re-send the conversation history.
5. **④ Prompt (and cost).** Every extra token in the prompt is paid for on every request.
6. **⑥ Output checks** (missing guardrail). Also question ③: why could the bot see card numbers at all?

## 📖 New words
| Word | Meaning in one line |
|------|---------------------|
| Interface (UI) | Where the user types and reads: chat window, website, app. |
| Backend | The code on a server that connects all the parts. |
| Retrieval | Finding the right pieces of your own data for a question. |
| Prompt | The full message sent to the model: instructions + data + history + question. |
| Hosted API | A model running on a provider's servers that you call over the internet. |
| Local model | A model running on your own machine. |
| Stateless | Has no memory between calls; every call starts fresh. |
| Conversation history | The earlier messages your code re-sends so the model "remembers." |
| Guardrails | Checks on the input or output to keep answers safe and correct. |
| Logs | A record of what the app did, used for debugging. |
| Evals | Tests that measure answer quality with numbers. |
